FOURENSICS

Evidence-based triage for GitHub issues and pull requests. A panel on the issue page shows what the code, at the version the reporter used, says about each claim, with links to the exact lines.

What it does

  • Lives in Chrome's side panel New

    Opens beside the GitHub page, like Chrome's own assistants, and follows whichever issue or pull request tab you're on. Light and dark themes follow your browser.

  • Checks each claim against the code

    Splits a report into individual claims, each tied to the reporter's exact words, and checks every claim against the repository's source, tests and docs.

  • The right version of the code

    Uses the commit, release or branch the reporter names, otherwise the code as it was when the report was written. Later fixes can't leak into the answer.

  • Evidence you can click

    Every finding links to the exact lines at that commit. Each claim gets two separate results:

    • supported
    • contradicted
    • inconclusive
    • reproduced
    • not reproduced
    • not attempted

  • Suggested label

    Proposes confirmed, invalid or cannot reproduce with its reasons, but only when the code or a reproduction backs it. Otherwise it says no label is suggested rather than guessing from the report's wording.

  • Pull requests too

    Compares the description with the diff, the changed tests and CI status. PR code is never run.

  • What's missing, and a reply draft

    Lists the details a report lacks (version, steps, error output, environment) and drafts a polite reply into the comment box. It never posts anything itself.

  • Honest about uncertainty

    Not finding something is never treated as proof a claim is false, and unverified results say so. Any language works; Python gets the deepest checks.

How it works

A fixed pipeline, not a free-running agent. The model (Gemma 4 26B by default) only extracts claims and reads collected evidence; it never runs commands.

  1. Read the issue or PR. Labels and maintainer comments are kept from the model.
  2. Pick the code version and check it out.
  3. Extract claims, files, symbols, errors and stack traces from the report.
  4. Run deterministic checks: does the code exist, where does the error come from, do the stack frames match, what tests and docs say.
  5. Record every observation as evidence with a hash and a permalink.
  6. The model interprets that evidence; rule-based checks then downgrade any verdict the evidence doesn't support.
  7. The panel shows the result, usually within a minute.

Install and use

You need Chrome 116 or newer (or another Chromium browser with side panels). The analysis runs on your own machine: macOS or Linux (on Windows, use WSL) with Python 3.11+ and Git.

  1. Install the extension. Download and unzip the file above. Open chrome://extensions, turn on Developer mode, click Load unpacked and select the unzipped folder. Pin FOURENSICS from the puzzle-piece menu so its icon stays in the toolbar.
  2. Try it without a backend (optional). Open the side panel's Settings (gear icon), tick Mock mode, and open any GitHub issue. The panel shows a bundled example result.
  3. Set up the analysis backend. 
    git clone https://github.com/IshanMaheshwari-777/FOURENSICS.git
cd FOURENSICS
python3 -m venv backend/.venv
backend/.venv/bin/pip install -e backend
cp backend/.env.example backend/.env
  4. Add your keys to backend/.env: a free Google AI Studio key as GOOGLE_API_KEY, and (recommended, to avoid GitHub's rate limits) a read-only GITHUB_TOKEN.
  5. Start the backend. It listens on http://localhost:8787, the extension's default. 
    scripts/dev.sh backend
  6. Open any public GitHub issue or pull request and click the FOURENSICS toolbar icon (or the FOURENSICS tab on the page's right edge). Untick Mock mode if you set it. The side panel fills in as checks finish and links each finding to the code.

Good to know

  • Read-only: it never comments, labels, or writes to a repository.
  • Public repositories only. Keys stay in your local .env.
  • Static checks can't settle everything: hardware, timing and environment-specific problems often stay inconclusive.
  • Results support a maintainer's judgement; they don't replace it.
